# レスポンシブ画面監査・最適化設計

## 目的

PC・タブレット・スマートフォンで、主要画面の横はみ出し、要素の重なり、主要操作の画面外退避、固定ナビゲーションとの干渉を解消する。PCは1366×768で主要操作を初期表示内へ収めることを優先し、スマートフォンは360×800で横スクロールなし・下部ナビゲーションと操作領域が重ならないことを必須とする。

## 対象範囲

- 新規ゲーム
- ダッシュボード
- 試合日程
- スカッド・固定起用
- 戦術・セットプレー
- 移籍・スカウト
- クラブ・スタッフ・理事会
- 記録・監督キャリア
- ライブ試合
- 共通モーダル・クラウド保存ダイアログ

ゲームロジック、セーブデータ形式、試合計算、既存機能の追加は対象外とする。

## 採用方針

共通シェルを先に調整し、その後に主要画面固有の崩れを修正する。CSSの数値縮小だけではなく、Playwrightによる実ブラウザ計測とスクリーンショット比較を導入する。

## レイアウト構造

### PC 1280px以上

- 1366×768を基準解像度とする。
- 左サイドバーは216px、右コンテキストパネルは264pxを基準幅とする。
- 中央領域は常に`minmax(0, 1fr)`とし、子要素の最小幅で画面全体を押し広げない。
- トップバーは64pxを基準高とする。
- コンテンツ余白、カード余白、見出し、操作ボタンを一段階コンパクト化する。
- サイドバーとコンテキストパネルは画面高に収まらない場合のみ内部スクロールさせる。
- ダッシュボードの次戦カード、主要指標、クイック操作を1366×768の初期表示内で確認できる密度にする。

### 中間幅 961～1279px

- 右コンテキストパネルを非表示にする。
- 1121～1279pxでは左サイドバーを216pxで表示する。
- 961～1120pxでは左サイドバーを82pxのアイコン型で表示する。
- 重要項目はダッシュボードの優先対応領域または既存通知導線から参照可能な状態を維持する。
- 2列・3列グリッドは内容の最小幅に応じて段階的に1～2列へ変更する。

### タブレット 681～960px

- 左サイドバーを82pxのアイコン型へ変更する。
- 右コンテキストパネルは表示しない。
- スカッド、ライブ試合、試合結果などの複合レイアウトは1列へ変更する。
- 表はページ全体ではなく`.table-wrap`内部だけ横スクロールを許可する。

### スマートフォン 680px以下

- サイドバーを非表示にし、下部ナビゲーションを5等分固定にする。
- 下部ナビゲーション自体の横スクロールは使用しない。
- `env(safe-area-inset-bottom)`を考慮し、コンテンツと固定操作バーに十分な下余白を設ける。
- 360×800と390×844でページ全体の横スクロールを発生させない。
- 長いタイトル、クラブ名、ボタン文言は省略表示または複数行化し、隣接操作を押し出さない。
- 2列の指標カードは幅が足りない画面では1列へ切り替える。
- 共通モーダルは下部シート型とし、本文のみ内部スクロール、ヘッダーと操作ボタンは固定表示する。
- ライブ試合はスコア、ピッチ、実況、操作の順に縦積みし、固定操作が下部ナビゲーションと重ならないようにする。

## コンポーネント別修正

### 共通シェル

`src/styles.css`のブレークポイントを整理し、PC・中間幅・タブレット・スマートフォンの4段階を明示する。境界値は1280px、1120px、960px、680pxを使用する。

### グリッド・カード

`.metrics-grid`、`.grid-2`、`.grid-equal`、`.dashboard-quick-actions`、`.project-grid`、`.award-grid`、`.match-plan-grid`などは、固定列数ではなく各画面幅で読みやすい列数に変更する。各子要素には`min-width: 0`を徹底する。

### 表

`.data-table`の最小幅は維持し、`.table-wrap`にのみ横スクロールを許可する。ページ全体の`scrollWidth`が`clientWidth`を超えないことをテストする。

### スカッド・ピッチ

PCではピッチと選手一覧の比率を調整し、1366×768で操作領域が過度に縦長にならないようにする。タブレット以下では縦積みにし、sticky要素を解除する。

### ライブ試合

PCでは最大高を画面内に収め、内部領域のみスクロールさせる。スマートフォンではスコアボードの固定幅を撤廃し、クラブ名・スコアが重ならない3列構成へ縮退する。

### モーダル

`max-height`、内部スクロール、safe-area、下部アクションのsticky化を統一する。320×568でも閉じる・キャンセル・決定操作へ到達できることを保証する。

## 実ブラウザ検証

Playwrightを導入または既存テスト構成へ追加し、以下のビューポートで主要画面を検査する。

| 区分 | ビューポート |
|---|---|
| 標準PC | 1366×768 |
| 大型PC | 1536×864 |
| 小型PC | 1024×768 |
| タブレット | 768×1024 |
| スマートフォン | 390×844 |
| 小型スマートフォン | 360×800 |
| 最小確認 | 320×568 |

## 自動判定項目

- `document.documentElement.scrollWidth <= document.documentElement.clientWidth`
- 固定ヘッダー、下部ナビ、固定操作バー同士が重ならない
- 主要操作ボタンがビューポートまたは内部スクロール領域から到達可能
- 下部ナビの5項目がビューポート幅内へ収まる
- モーダルの閉じる・決定ボタンが常時表示される
- スマートフォンの主要タップ操作は44×44px以上の操作領域を持つ
- JavaScript例外とコンソールエラーが発生しない

## スクリーンショットレビュー

各ビューポートでダッシュボード、スカッド、移籍、クラブ、ライブ試合、モーダルのスクリーンショットを保存する。差分画像だけで合否を決めず、横はみ出し・重なり・情報密度・操作導線を目視確認する。

## テスト戦略

1. 現行`main`でPlaywright監査を実行し、失敗条件とスクリーンショットを基準として保存する。
2. 共通シェルの失敗テストを追加する。
3. CSSと必要最小限のレンダリング構造を修正する。
4. 画面固有の失敗を1件ずつ修正する。
5. 既存のNodeテスト、品質検査、HTTPスモーク、production buildをすべて再実行する。
6. Playwright全ビューポートを再実行し、スクリーンショットをレビューする。

## 完了条件

- 指定7ビューポートでページ全体の横スクロールがない。
- 対象10画面で要素の重なり、操作不能、閉じられないモーダルがない。
- 1366×768のダッシュボードで次戦情報、主要指標、主要操作が初期表示内に収まる。
- 360×800で下部ナビが5等分表示され、コンテンツ・固定操作と重ならない。
- 既存140テストを含む全テスト、品質検査、HTTPスモーク、production buildが成功する。
- コードレビューで重大・高優先度の未修正事項がない。
